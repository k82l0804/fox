# Spec 03: Session Management & History

> Technical specification for ACP session lifecycle, multi-session state tracking, notification routing (`sessionUpdate`), and conversation history persistence.

---

## 1. Overview & Architecture

An ACP **Session** represents a single stateful conversation thread between the user (via the VSCode extension) and the coding agent (Fox CLI). The `SessionManager` orchestrates session creation, prompt dispatch, active turn cancellation, configuration changes, and history synchronization.

## 2. Session Data Model

Each session is encapsulated in a strongly typed data structure:

```typescript
import type {
  InitializeResponse,
  SessionModeState,
  SessionModelState,
  SessionConfigOption,
  AvailableCommand,
} from "@agentclientprotocol/sdk";

export interface SessionInfo {
  sessionId: string;
  agentId: string;
  agentName: string;
  agentDisplayName: string;
  cwd: string;
  createdAt: string;
  initResponse: InitializeResponse;

  /** Operational modes (e.g. "code", "architect", "ask") */
  modes: SessionModeState | null;

  /** Active and available models */
  models: SessionModelState | null;

  /**
   * Generic session config options (ACP v0.21+).
   * Supersedes modes/models when supported by the agent.
   */
  configOptions: SessionConfigOption[] | null;

  /** Slash commands advertised by the agent (e.g. /help, /compact) */
  availableCommands: AvailableCommand[];

  /** Display title (auto-generated by LLM or updated via session_info_update) */
  title?: string;

  /** Summary of execution plan / checklist items */
  activePlan?: ExecutionPlan;
}
```

## 3. Session Lifecycle Operations

### 3.1. `newSession`
When starting a conversation or switching workspaces:
1. Gathers the current workspace root directory (`cwd`).
2. Discovers configured MCP servers via `McpConfigLoader`.
3. Calls ACP `connection.newSession({ cwd, mcpServers })`.
4. Fox CLI registers the session in SQLite, mounts MCP servers, and returns:
   ```json
   {
     "sessionId": "sess_01J8ABC123...",
     "modes": {
       "currentModeId": "code",
       "availableModes": [
         { "id": "code", "name": "Code Mode", "description": "Full edit access" },
         { "id": "ask", "name": "Ask Mode", "description": "Read-only assistance" }
       ]
     },
     "configOptions": [
       {
         "id": "model",
         "name": "Model",
         "currentValue": "gpt-4o",
         "options": [
           { "value": "gpt-4o", "label": "GPT-4o (Default Local Proxy)" },
           { "value": "qwen2.5-coder", "label": "Qwen 2.5 Coder 32B" }
         ]
       }
     ]
   }
   ```
5. Registers `SessionInfo` in the active session map.
6. Synchronizes `workspaceState` with the new session identifier.
7. Emits `active-session-changed` to update the webview and status bar.

### 3.2. `sendPrompt`
When the user submits a message in the composer:
1. Validates that an active session exists.
2. Formats prompt content into ACP `ContentBlock[]`:
   - Text chunks (`{ type: "text", text: "..." }`).
   - File attachment references (`{ type: "resource", resource: { uri: "file://...", text: "..." } }`).
   - Image attachments (`{ type: "image", source: { type: "base64", mediaType: "image/png", data: "..." } }`).
3. Sets `turnInProgress = true` in extension context.
4. Invokes `connection.prompt({ sessionId, prompt: contentBlocks })`.
5. **ACP v2 turn tracking:** In ACP v2, `session/prompt` returns an immediate empty acknowledgment `{}`. Turn execution state is tracked via `state_update` notifications:
   - `{ state: "running" }` — agent is executing.
   - `{ state: "requires_action" }` — agent is waiting for elicitation response.
   - `{ state: "idle", stopReason: "completed" | "cancelled" | "error" }` — turn finished.
6. Resets `turnInProgress = false` upon receiving `state_update` with `state: "idle"`.


### 3.3. `cancel`
When the user clicks the Cancel button or presses `Escape`:
1. Checks that `turnInProgress` is active.
2. Invokes `connection.cancel({ sessionId })`.
3. Fox CLI aborts its local `AbortController`, terminates running shell child processes, and sends a terminal state update.
4. Webview renders a subtle badge: `Turn cancelled by user`.

### 3.4. `loadSession` & `listSessions`
For resuming previous conversations:
1. If Fox CLI advertises `capabilities.listSessions = true`, calls `connection.listSessions({ cwd })`.
   - Populates the **Agents & Sessions** tree view with historical sessions from SQLite.
2. When the user clicks a historical session:
   - Sets webview into loading state (`notifyLoadSessionStart`).
   - Calls `connection.loadSession({ sessionId, cwd, mcpServers })`.
   - Fox CLI rehydrates conversation turns from SQLite and replays prior messages via `sessionUpdate`.
   - Restores session configuration, modes, and plan status.
   - Clears loading overlay and focuses the chat panel.

### 3.5. `closeSession`
When switching sessions without permanently deleting history:
1. Invokes `connection.sessionClose({ sessionId })`.
2. Fox CLI saves any unsaved turn state and cleans up its in-memory session data.
3. The session remains visible in `listSessions` (it can be re-opened with `loadSession`).
4. Local `SessionInfo` is removed from the active session map.

### 3.6. `deleteSession`
When the user explicitly removes a session from history:
1. Confirms deletion in a modal: `Permanently delete this session? This cannot be undone.`
2. Invokes `connection.sessionDelete({ sessionId })`.
3. Removes the session from both the active map and `workspaceState` cache.
4. Updates the Session Tree View to reflect removal.

### 3.7. `forkSession` (Session Branching)
When the user wants to explore an alternative direction without losing the current conversation:
1. Invokes `connection.sessionFork({ sessionId, cwd })`.
2. Fox CLI duplicates conversation history up to the current turn and registers a new `sessionId`.
3. The new session appears in the Session Tree View under the original session.
4. The client switches to the forked session (calls `loadSession` with the new ID).
5. MCP servers are re-injected from `McpConfigLoader` for the new session.

> **Use case:** Explore "what if I refactor this instead" paths non-destructively.

### 3.8. `additionalDirectories` (Multi-Root Workspaces)
For multi-root workspaces, both `newSession` and `loadSession` accept an `additionalDirectories` parameter:
```typescript
await connection.newSession({
  cwd: primaryWorkspaceRoot,         // workspaceFolders[0]
  additionalDirectories: otherRoots, // workspaceFolders[1..n]
  mcpServers,
});
```
> **V1 Scope:** `additionalDirectories` population is deferred to V2. The V1 implementation uses only `workspaceFolders[0]` as `cwd` and sends an empty `additionalDirectories`. See [Spec 07 §2](./07-mcp-forwarding-and-configuration.md) for the scoping note.

## 4. Notification Routing (`sessionUpdate`)

Fox CLI streams events via `connection.sessionUpdate({ sessionId, update })`. The `SessionUpdateRouter` demultiplexes updates to appropriate subscribers.

### Event Routing Table

| Update Field | Payload Data | Router Target | UI Behavior |
|---|---|---|---|
| `sessionUpdate: "agent_message_delta"` | `{ delta: { text: string } }` | Webview Chat | Appends streaming Markdown chunk to active assistant message card. |
| `sessionUpdate: "thought_message_delta"` | `{ delta: { text: string } }` | Webview Chat | Appends streaming tokens to the collapsible reasoning container (`<think>`). |
| `sessionUpdate: "tool_call_start"` | `{ toolCallId, name, input }` | Webview Chat | Displays pending tool card with animated spinner and input parameters. |
| `sessionUpdate: "tool_call_update"` | `{ toolCallId, outputDelta }` | Webview Chat | Streams real-time stdout/stderr inside the tool output container. |
| `sessionUpdate: "tool_call_complete"` | `{ toolCallId, status, output }`| Webview Chat | Updates card badge (`Completed` / `Failed`) and renders final output payload. |
| `sessionUpdate: "plan_update"` | `{ entries: PlanEntry[] }` | Plan Widget | Updates interactive checklist with statuses (`todo`, `in_progress`, `completed`). |
| `sessionUpdate: "state_update"` | `{ state: string, stopReason?: string }` | Session Manager | Tracks turn execution state (`"running"`, `"requires_action"`, `"idle"`). Signals turn completion when `state: "idle"`. |
| `sessionUpdate: "usage_update"` | `{ used: number, size: number }` | Context Progress | Computes utilization percentage (`used / size`), emits `usageUpdate` to webview for `ContextProgress` bar. **Cost fields are ignored.** |
| `sessionUpdate: "notice"` | `{ level: string, message: string }` | Notice Banner | Routes advisory messages to a dismissible `NoticeBanner` toast above the composer. |
| `sessionUpdate: "terminal_update"` | `{ terminalId: string, cols: number, rows: number }` | Terminal Stream View | Creates or resizes an `@xterm/xterm` terminal panel in the webview. |
| `sessionUpdate: "terminal_output_chunk"` | `{ terminalId: string, data: string }` | Terminal Stream View | Writes a base64-decoded VT100 byte sequence into the xterm terminal buffer. |
| `sessionUpdate: "available_commands_update"`| `{ commands: AvailableCommand[] }`| Composer Autocomplete | Updates slash command suggestions list. |
| `sessionUpdate: "session_info_update"` | `{ title?: string }` | Webview & Tree | Updates chat title banner and session tree node text. |


### Microtask Race Guard (`drainPending`)
Because `@agentclientprotocol/sdk` dispatches incoming notifications asynchronously, early notifications (such as `available_commands_update` or initial `plan_update`) can arrive before the `newSession` RPC promise resolves in TypeScript.

To prevent dropped events:
1. Notifications arriving for an unregistered `sessionId` are buffered into memory maps:
   - `pendingAvailableCommands: Map<string, AvailableCommand[]>`
   - `pendingConfigOptions: Map<string, SessionConfigOption[]>`
   - `pendingTitles: Map<string, string>`
2. As soon as `newSession` resolves, `SessionManager.drainPending(sessionInfo)` extracts all buffered entries and applies them immediately.

## 5. Session Configuration & Modes

Fox ACP Client supports both legacy `modes`/`models` and the modern **Session Config Options** protocol introduced in ACP v0.21.

### Priority Rule
Per the ACP specification, when an agent returns both `configOptions` and `modes`/`models`, the client **must prioritize `configOptions` exclusively**.

```typescript
export class SessionManager {
  async setMode(sessionId: string, modeId: string): Promise<void> {
    const conn = this.getConnection(sessionId);
    await conn.setSessionMode({ sessionId, modeId });
    const session = this.sessions.get(sessionId);
    if (session?.modes) {
      session.modes.currentModeId = modeId;
      this.emit("mode-changed", sessionId, modeId);
    }
  }

  async setConfigOption(sessionId: string, configId: string, value: string): Promise<void> {
    const conn = this.getConnection(sessionId);
    await conn.setSessionConfigOption({ sessionId, configId, value });
    // Update local cached config options
    const session = this.sessions.get(sessionId);
    const option = session?.configOptions?.find(o => o.id === configId);
    if (option) {
      option.currentValue = value;
      this.emit("config-option-changed", sessionId, configId, value);
    }
  }
}
```

## 6. History Store & Synchronization (`HistoryStore`)

### Tiered Persistence Model

1. **Tier 1: Fox CLI Session Retrieval via ACP** (Primary):
   - Fox CLI is the authoritative store of truth for conversation history (persisted internally in SQLite on the server side).
   - The client **never reads SQLite directly** — all history access occurs via the ACP protocol RPCs `session/list` and `session/load`.
   - Sessions persist across VSCode restarts, OS reboots, and CLI sessions.
   - The `HistoryStore` class on the client side is purely a cache coordinator, not a database adapter.
2. **Tier 2: Client `workspaceState` Cache** (Local Fallback):
   - Stores an index of `SessionMetadata`:
     ```typescript
     interface CachedSessionItem {
       sessionId: string;
       agentName: string;
       cwd: string;
       createdAt: string;
       title: string;
       lastActiveAt: string;
     }
     ```
   - Used to render the tree view instantly on editor startup before the agent process is spawned.
   - Provides history tracking even when connecting to simpler third-party ACP agents that lack `session/list` support.

## 7. Error Handling

### Session Lifecycle Error Contracts

| Operation | Error Condition | Behavior |
|---|---|---|
| `newSession` | Agent returns JSON-RPC error | Display error in chat panel: `Failed to create session: ${error.message}`. Log full error. Do not transition to active state. |
| `newSession` | MCP server discovery fails (malformed JSON) | Log warning. Proceed with `mcpServers: []` and show notification: `Some MCP server configurations could not be loaded.` |
| `sendPrompt` | No active session | Display inline error in composer: `No active session. Click "New Conversation" to start.` |
| `sendPrompt` | Agent returns error mid-turn | Mark turn as failed. Append error message as a system message in the chat. Reset `turnInProgress = false`. |
| `loadSession` | Session ID not found by agent | Remove stale entry from `workspaceState` cache. Show: `Session no longer available. It may have been deleted.` |
| `loadSession` | Agent does not support `loadSession` capability | Hide session tree entries. Show notification: `This agent does not support session history.` |
| `cancel` | Cancel sent but turn already completed | Silently ignore (no-op). |
| `setConfigOption` | Agent rejects value | Revert local cached value. Show notification: `Failed to update ${configId}: ${error.message}`. |
